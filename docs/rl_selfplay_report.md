# FOR-42 — отчёт: первый PPO / self-play агент FormicMind

**Вердикт пилота: GO (технически и по наблюдаемому сигналу обучения), с оговорками ниже.** Реальный цикл
«решение → полный матч → награда → PPO-обновление → новый матч» работает на GPU RTX 5080 с 10 CPU-воркерами: веса
меняются только по наградам за исход матчей, действия стохастические и разнообразные, ошибок контроллера и
невалидных действий нет. Агент выучил **узкую стратегию — ранний «солдатский раш»**, а не общее сильное
поведение: против слабых ботов она работает, против raider и частично balanced результат зависит от seed. Рост
винрейта не обещался и не подтверждён как устойчивый — это измерено и описано ниже.

Протокол (зафиксирован и закоммитён до запусков): [rl_selfplay_protocol.md](rl_selfplay_protocol.md). Код:
`src/formicmind/rl/`, тесты: `tests/test_rl_*.py` (40 штук), сырые результаты: `results/rl_for42/`.

## 1. Что реализовано

- **Стохастические действия с корректным `log_prob`** над неизменённым декодером: латентное действие
  (masked Categorical для lay/army, условный Bernoulli для avoid только при наличии выбора, Categorical на размер
  поддержки forage k∈{1,2,3}, упорядоченный выбор k целей без возвращения, logistic-normal для долей) → 17 логитов →
  штатный `decode_action_logits`. PPO считает `log π` **того же латента** при тех же масках. ([distribution.py](../src/formicmind/rl/distribution.py))
- **Actor–critic 223→256→256→256**: отдельные головы политики (32 выхода + обучаемый `log_std`) и **отдельный** critic
  (~197k + ~189k параметров).
- **Награда**: терминал +1/0/−1 (таймаут `T_max` — ничья 0); усечение — без награды, с bootstrap; опциональный
  potential-based shaping (в P1 выключен, в P2 коэффициент 0.05).
- **PPO-Clip**, GAE (γ=0.997, λ=0.95), value loss, энтропийный бонус (раздельный для дискретных и гауссовых голов),
  нормализация advantage, градиентный клип, мониторинг KL/clipfrac, ранняя остановка по KL, строго on-policy батчи.
- **Self-play**: текущие веса (зеркало, данные обоих мест) и неизменяемые замороженные snapshot'ы с SHA-256;
  детерминированный планировщик `(run_seed, iteration)`; уникальные seed'ы матчей; независимые RNG-потоки политик.
  Карты: 6 именованных + процедурные `gen:*` для обучения, **отдельный held-out набор** карт для оценки.
- **Параллельность**: CPU-воркеры `spawn` (Windows), обучение на GPU; тест побайтовой идентичности траекторий
  inline и в двух spawn-процессах.
- **Checkpoint/resume** с проверкой SHA-256 и контрактных версий; resume побитово воспроизводит веса (проверено на CPU; на GPU побитовость не заявляется).
- **Независимая оценка** на фиксированных матчах (seed ≥ 9·10⁹, карты held-out), оба места, режимы `sample`/`greedy`.
  Веса по оценке не обновляются; гиперпараметры не подбирались.

Не менялись: физика, правила, `rules_version`, балансы, `ActionV2`, `ObservationV2`, декодер, базовые боты, замороженные
датасеты и артефакты FOR-25/35/37/38/40. Ни одно действие Balanced v2 (или другого бота) не используется как метка.

## 2. Проверки корректности (до реальных матчей)

| Что проверено | Тест |
|---|---|
| нормировка дискретной массы (полное перечисление всех латентов, 6 разных масок) | `test_discrete_probability_mass_sums_to_one` |
| `log_prob` совпадает с независимой float64-переформулировкой | `test_torch_log_prob_matches_independent_reference` |
| сэмплы всегда легальны; декодер воспроизводит латент (lay/army/avoid/поддержка/доли ±2 из Q=65535) | `test_sampled_actions_always_legal_and_decode_to_the_latent`, реальные маски + `validate_action` |
| замаскированное не сэмплируется; принудительный avoid даёт log-prob 0; частоты сэмплов = вероятностям | три отдельных теста |
| конечность на экстремальных логитах, градиенты | `test_extreme_logits_stay_finite_and_gradients_flow` |
| GAE (terminal vs truncated, padding) = эталонный цикл; truncation bootstrap'ится, terminal нет | `test_gae_*`, `test_truncation_*` |
| ratio=1 при тождественных весах; клип блокирует градиент; нефинитные данные отвергаются | `test_ppo_*`, `test_non_finite_*` |
| **игрушечные бандиты с известным ответом** (lay=soldier∧raid → награда 1; доля на центр) решены только по наградам | `test_ppo_solves_a_contextual_bandit_with_a_known_answer` |
| терминальная нулевая сумма, телескопирование и границы shaping, idle ⇒ ничья 0, усечение без награды | `test_rl_reward_rollout.py` |
| политика видит ровно записанное `ObservationV2`; записанные действия = то, что исполнил движок | `test_policy_input_*`, `test_recorded_actions_*` |
| независимость RNG: тот же seed ⇒ тот же матч, другой seed/место ⇒ другие сэмплы | `test_policy_rng_streams_*` |
| spawn-воркеры ≡ inline; resume побитово ≡ непрерывному обучению; повреждённый checkpoint отвергается | `tests/test_rl_train.py` |

Полный набор: `pytest -q` — **1194 passed** локально (138 с). CI: см. PR.

## 3. Параметры и происхождение

Общие для P1/P1b/P1c/P2: 80 итераций × 128 полных матчей = **10 240 матчей**, K=30, `T_max`=3000, PPO clip 0.2,
lr 3e-4, 4 эпохи, minibatch 512, `target_kl` 0.05, `ent_coef` 0.01 / 0.001 (доли), p(current)=0.5 иначе snapshot
(новый каждые 5 итераций, ≤12 активных), 50% карт процедурные, `baseline_sparring`=0 (боты в обучении **не участвуют**).
Seed'ы матчей `4 200 000 000 + индекс`, оценка `≥ 9 000 000 000`. Запуск: `python -m formicmind.rl train --out … --set run_seed=N`.
Железо: Windows 11, RTX 5080 (CUDA, torch 2.15+cu134), 12 логических CPU, 10 воркеров.

## 4. Доказательства того, что агент учится сам

- Веса меняются на каждой итерации (`param_delta_l2` > 0), все потери конечны; расхождение ratio при тождественных
  весах между CPU-сэмплированием и GPU-пересчётом ≤ 6·10⁻⁶ (`identity_ratio_max_dev`).
- **Поведение изменилось радикально** (P1; KL(init‖final) на 248 пробных состояниях из матчей ботов): lay 3.19,
  army 1.80, forage-цели 1.27. Доля `lay=soldier`: 35% → 99%; `army`: raid 14% → 43%, garrison 14% → 43%, оборона узла N4 12%; доля
  forage на «home» ≈ 0; энтропия дискретных голов 7.97 → 4.21. Средняя длина матча 303 → 152 тика (в P1b/P1c — около 290–300 тиков).
- Гейты протокола: **T1–T4 пройдены во всех четырёх запусках**; L1 (счёт против необученной `init` ≥0.60): 0.90 / 1.00 / 0.975 / 0.95;
  L3 (полная вариация lay/army ≥0.10): 0.58–0.71 во всех запусках.
- Внутренняя согласованность: финальная политика против собственной копии (snapshot итерации 80) набирает 0.55 / 0.50 / 0.51 / 0.54 ≈ 0.5.
  Против snapshot'а итерации 40: 0.93 / 0.86 / 0.75 / 0.86 — самообучение прогрессирует и между итерациями.

## 5. Независимая оценка (финальный checkpoint, suite `full`, `sample`, 11 карт × 2 места × 2 повтора = 40 матчей на строку)

Счёт = (победы + ½ ничьи) / матчи; в скобках W-D-L.

| Противник | P1 (42) | P1b (43) | P1c (44) | P2 shaping (42) |
|---|---|---|---|---|
| init (необученная) | 0.90 (36-0-4) | 1.00 (40-0-0) | 0.97 (39-0-1) | 0.95 (38-0-2) |
| random v2 | 0.93 (37-0-3) | 1.00 | 0.97 | 1.00 |
| turtle v2 | 1.00 | 1.00 | 1.00 | 1.00 |
| rush v2 | 0.65 (26-0-14) | 0.80 (32-0-8) | 0.60 (24-0-16) | 0.85 (34-0-6) |
| balanced v2 | 0.64 (25-1-14) | **0.05** (2-0-38) | **1.00** (40-0-0) | 0.49 (19-1-20) |
| raider v2 | **0.12** (5-0-35) | 0.15 (6-0-34) | 0.47 (19-0-21) | 0.28 (11-0-29) |

Все 480 матчей каждой оценки завершились исходом (0 усечений); причины: почти всегда `queen_death`, редко
`economic_collapse`. Режим `greedy` даёт ту же картину (1.0 против init/random/turtle). Срез «классическая карта /
held-out карты» — в `eval/final_full.json` (`indist` / `heldout`); для 20 матчей на ячейку разброс ±0.2, поэтому
различия между картами не интерпретируются.

**Что это значит.**
1. Против init/random/turtle обучение даёт стабильный, воспроизводимый во всех seed'ах выигрыш.
2. Против rush результат положительный в трёх из четырёх запусков; против balanced и raider **результат
   определяется seed'ом** (balanced: 0.05…1.00; raider: 0.12…0.47). Разные seed'ы находят разные узкие стратегии
   (в P1c — оборона узла N4 82% + рейд 16%; в P1b — рейд 64% + оборона центра 33%), и каждая эксплуатируема отдельными ботами. Это ожидаемая
   проблема self-play без разнообразия оппонентов, а не сбой реализации.
3. Shaping 0.05 (P2) не показал преимущества над терминал-only на фоне межсидового разброса (n=1 seed); вывода о нём не делаем.
4. Стратегия «убей королеву за 100–300 тиков» означает, что длинную экономику (вплоть до `T_max`=3000) агент в пилоте
   фактически не осваивал: матчи короткие, `economic_collapse` редок.

Колебания счёта в мониторинговых оценках по ходу P1 (10 матчей на противника: balanced 0.7→0.2→0.1→0.65) показывают
нестационарность self-play; они не использовались для выбора чего-либо.

## 6. Производительность (измерено, `results/rl_for42/bench_w{1,5,10}.json`, профайлер раньше любой оптимизации)

| Воркеры | эпизодов/с, матчи свежей политики (~290 тиков) | решений/с | тиков/с | эпизодов/с, полные матчи 3000 тиков | инженерное время/тик/воркер |
|---|---|---|---|---|---|
| 1 | 22.4 | 453 | 6 542 | 3.0 | 0.11 мс |
| 5 | 79.0 | 1 602 | 23 120 | 10.9 | 0.15 мс |
| **10** | **118.4** | **2 401** | **34 650** | **16.6** | 0.20 мс |

- Узкое место сбора — **движок** (`step_tick`, ≈80% времени воркера: harvest/upkeep/dispatch/routing); инференс политики
  ≈0.93 мс на решение (≈20%). Движок менять нельзя, поэтому оптимизация не проводилась; инференс не является узким местом.
- Масштабирование по воркерам сублинейное (1→10: ×5.5), т.к. 12 логических ядер и общие кэши; тики на воркер замедляются 0.11→0.20 мс.
- Обновление PPO: на GPU 391 тыс. sample-эпох/с против 109 тыс. на CPU (×3.6); типичное обновление пилота занимает 0.1 с
  против 0.5–4 с сбора ⇒ GPU почти простаивает (единственный отсчёт утилизации во время самого обновления — 21%); система **CPU-bound**.
- В реальных пилотах (матчи короткие) средняя скорость 70–230 эпизодов/с; 10 240 матчей обучаются за ~1–1.5 минуты.

## 7. Масштабирование до сотен тысяч и миллионов матчей (подготовка; в этом тикете не запускалось)

Инфраструктура готова: `--set iterations=… --set max_matches=… --set max_wall_seconds=…`, resume по `latest.json`, неизменяемые
snapshot'ы (разрежение активного пула `max_active_snapshots`), метрики JSONL, оценка suite `full` по расписанию.

Оценка времени на текущем железе (10 воркеров): при выученных коротких матчах 70–230 эп/с ⇒ **100 тыс. ≈ 10–25 мин, 1 млн ≈ 1.5–4 ч**;
при полных матчах (агент, переживающий до `T_max`) 12–17 эп/с ⇒ **100 тыс. ≈ 1.7–2.3 ч, 1 млн ≈ 17–23 ч**. Размеры файлов растут
линейно (≈0.2 МБ метрик на 10 тыс. матчей; snapshot ≈0.8 МБ каждые 5 итераций).

Что стоит сделать *до* простого увеличения числа матчей (кандидаты для отдельной задачи; в этом тикете **не** реализовано и не
подбиралось по оценке):
1. **Разнообразие оппонентов**: лига из snapshot'ов + фиксированная доля обучающих спарринг-матчей с ботами (опция
   `baseline_sparring` уже есть; нужен чистый протокол, чтобы это не превращалось в imitation), иначе каждый seed
   сходится к своей эксплуатируемой стратегии.
2. **Устойчивость к коллапсу энтропии**: энтропийное расписание/нижняя граница, больший `matches_per_iteration` (≥512) для
   менее шумных обновлений и более редкая смена snapshot'ов.
3. **Длинная игра**: метрики экономики (выживание, голод, солдаты/рабочие) и кривая «длина матча»; проверка, что агент вообще
   достигает продвинутых фаз; при необходимости ограничение раннего рейда через разнообразие соперников, а не через правила награды.
4. **Больше n в оценке** (≥200 матчей на ячейку) и 3+ seed'а на каждый вариант — текущие 40 матчей дают ±0.15 на ячейку.
5. Если понадобится скорость: пакетный инференс по нескольким матчам в одном процессе (не основное узкое место) или больше процессов на машине с большим числом ядер.

## 8. Ограничения и честные оговорки

- Пилот проверяет **корректность и наличие сигнала обучения**, а не качество игры; 4 запуска (3 seed'а без shaping) —
  мало для научных выводов.
- Оценка по 40 матчей на ячейку (много ячеек с детерминированными ботами и одним стохастическим игроком) — доверительные
  интервалы широкие; счёт приведён вместе с W-D-L.
- Value-оценки для GAE считаются на стороне обучения (GPU) теми же весами, что собирали данные (on-policy, идентично
  записи в воркере); в траектории хранятся `old_logp`, латент, маска, наблюдение, исполненное `ActionV2`, награда, флаги.
- Усечение (`max_ticks` кратное K) реализовано и покрыто тестами, в пилотах не использовалось (матчи полные).
- Ветка создана от `origin/main` (PR #22 FOR-38); PR FOR-40 (#23) на момент работы ещё не влит и не нужен для FOR-42,
  поэтому конфликтов нет. Постороннее (`.idea/`, `results/gate0_*.json`, `results/starvation_confirm_posthoc/posthoc.json`,
  `E:\fm35check`) не тронуто и не закоммичено.

## 9. Воспроизведение

```bash
.venv/Scripts/python -m formicmind.rl train --out results/rl_for42/p1_seed42 --set run_seed=42 --set device=cuda --set workers=10
.venv/Scripts/python -m formicmind.rl eval  --run results/rl_for42/p1_seed42 --suite full --workers 10 --vs-snapshots 8 16 \
    --output results/rl_for42/p1_seed42/eval/final_full.json
.venv/Scripts/python -m formicmind.rl analyse --run results/rl_for42/p1_seed42 --eval results/rl_for42/p1_seed42/eval/final_full.json \
    --output results/rl_for42/p1_seed42/analysis.json
.venv/Scripts/python -m formicmind.rl bench --workers 10 --matches 160 --output results/rl_for42/bench_w10.json
```

Реплики: `results/rl_for42/run_replicates.sh`. Файлы запуска: `config.json`, `metrics.jsonl` (по строке на итерацию +
оценки), `eval/*.json`, `analysis.json`, `summary.json`, последний checkpoint и snapshot'ы (для P1 — все).
