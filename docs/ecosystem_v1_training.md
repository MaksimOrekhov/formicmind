# Ecosystem v1: первое реальное обучение (FOR-49, E3-a)

Первая обучаемая сеть для E1: восемь колоний одного мира управляются одной сетью (режим `mirror`), у каждой колонии — своя GRU-память и свой поток случайных чисел. Обучение идёт на настоящем `step_world_tick`, на свежих картах, по награде за жизнеспособность колонии. Ни эвристики, ни `random_valid` не используются как учителя; они только точки сравнения при оценке.

## Запуск

```bash
python -m formicmind.eco train --out runs/first --iterations 120 --worlds 16 --workers 11 --seed 1 --eval-every 20 --eval-worlds 8
python -m formicmind.eco eval --model runs/first/final --worlds 8 --workers 11 --out runs/first/eval.json --replay-out replay.jsonl --replay-seed 90000 --verify --decisions replay.decisions.jsonl
python -m formicmind.eco replay-verify replay.jsonl --model runs/first/final --decisions replay.decisions.jsonl
```

Нужен PyTorch (`pip install torch`; в CI — CPU-сборка). Короткая команда для проверки цепочки (секунды): `train --iterations 2 --worlds 2 --ticks 120 --eval-worlds 1 --out tmp`. Импорт `formicmind.eco` и CLI PyTorch не загружает: он подключается только командами `train`, `eval` и при `--model`.

`train` пишет в `--out`: `config.json`, `metrics.jsonl` (строка на итерацию), `latest/` (веса после каждой итерации), `final/`, `eval_final.json` (оценка на отложенных картах рядом с базовыми политиками). Модель — каталог `weights.pt` + `manifest.json` (схема, версии `ObservationE1/v2` и `ActionE1/v1`, конфигурация сети, SHA-256 весов, как обучена); загрузчик отказывается от модели с другими версиями или чужим хэшем.

## Награда: viability по тикам мира (`eco/viability.py`)

`ViabilityTracker` смотрит на мир **снаружи** (после каждого `step_world_tick`), читает только собственное состояние колонии (её когорты, склад, матка) и собственные счётчики тика (доставка в её гнездо, начисленное содержание). Другие колонии, карта, убийства и бои в награду не входят. Целочисленные EMA с обновлением **каждый тик**:

```
E_pop  += (workers + soldiers/2 - E_pop) / 300      income += (доставлено - income) / 120      burn += (содержание к уплате - burn) / 120
pop = min(1, E_pop/60)    runway = склад / (burn - income) при burn > income, иначе ∞    security = min(1, runway/40)
v = queen_alive * (0.6 pop + 0.4 security),    v_q = floor(65536 v)
```

* **[ВЫБОР]** контракт задаёт τ только для популяции (300 тиков); для дохода и расхода взято τ = 120 тиков (четыре плановых окна): поставки лежат комками. Это то же время памяти, что у оконных EMA наблюдения (вес 1/4 за 30 тиков).
* Интервал решения `[t_i, t_{i+1})` даёт `r_i = Σ v_q/(Q·H)` и `r_i^γ` (дисконт внутри интервала `γ_tick^k`), `γ_i = 0.997^(Δ_i/30)`, `λ_i = 0.95^(Δ_i/30)`. Награда зависит только от прошедших тиков: alert (10 тиков) ничего не добавляет.
* Гибель матки (или `collapse`) в тик `τ_d` даёт `v_q(τ_d) = 0`; последний интервал заканчивается в `τ_d + 1` (решение, принятое в начале того же тика, всё равно получает интервал длиной ≥ 1), штраф `−1.0` платится **один раз** в нём. Вымирание сирот после этого награды не меняет: трекер колонию больше не читает.
* Обрыв по горизонту (или `--ticks` короче 6000) — **усечение**: последний интервал бутстрэпится значением **обучаемого критика** на финальном наблюдении (движок формирует его для живых колоний), никогда не viability. Терминальный интервал `B = 0` и цепочка `A` на нём обрывается.
* Для PPO интервальные награды умножаются на `reward_scale = 10` (нормировка тренера: сырая награда имеет масштаб `1/H`); advantage всё равно нормируется по батчу. Метрики и отчёты используют недисконтированную награду без масштаба.

Тесты T-21/T-22 (`tests/test_eco_reward.py`) сверяют боевые функции `interval_rewards` и `gae_intervals` с независимой эталонной арифметикой `scripts/ecosystem_reward_ref.py` для разбиений 200×30, 600×10, смешанного (с alert) и нерегулярного, для гибели и усечения; проверяют, что след на реальном мире (seed 50004, рейдер 3: матка колонии 0 убита в тике 2621) кончается в тике гибели, штраф платится один раз, а трекер совпадает с независимым пересчётом из сырых данных тика и не читает чужое состояние.

## Сеть (`eco/rl/network.py`)

Входы — только `ObservationE1` и производные от него маски (`features.step_batch`); все слоты локальные, мировых id нет. 430 тыс. параметров.

* граф известных узлов: признаки узла + флаги легальности (forage / scout / guard из масок) + embedding вида; два раунда передачи сообщений по известным рёбрам (с признаками ребра), LayerNorm;
* множества: свои когорты (с embedding узла и цели), чужие колонии (с embedding известного гнезда), sightings (узел + колония), события памяти; mean+max-пулинг; глобальные признаки; embedding «домашнего» узла;
* слияние → 128; **две отдельные GRUCell**: у актёра и у критика (собственная память у каждого, у каждой колонии своя); голова ценности — отдельный MLP;
* головы: категориальные (egg, soldier share, flee, forage fraction, k, scout n, число скаутов-целей, миссия и размер каждого из трёх отрядов), средние долей `mu`, pointer-оценки по узлам (forage, scout, guard×3) и по парам «узел+колония» (attack×3).

Полная траектория колонии (около 200 решений за 6000 тиков) прогоняется через GRU целиком из нулевой памяти (без усечённого BPTT по кускам по 32, как предполагала миграция: траектории короткие, и так нет смещения из-за обрезки).

## Стохастическая политика (`eco/rl/distribution.py`)

Выборка идёт по ветвям декодера: egg, доля солдат, flee, доля добытчиков → при доле > 0 число целей `k ∈ 1..min(3, легальных)`, `k` целей **без возвращения** (Plackett–Luce, порядок учитывается), `k` вещественных логитов долей `z_j ~ N(mu_j, σ_j)` → число разведчиков → 1–2 цели без возвращения → три отряда (миссия с учётом оставшихся свободных солдат, размер 1–4, цель-узел или пара). Результат записывается в латентный вектор декодера, и **действие получает общий `decode(latent, masks)`**; тест `test_the_shared_decoder_reproduces_every_sampled_choice` прогоняет сотни реальных наблюдений через разные сети (выборка и greedy) и сверяет каждое решение декодера с выбором, включая все ветви (guard, attack, withdraw, 3 цели, 2 разведчика).

`log_prob` — это логарифм вероятности **этого** сэмпла; `evaluate` пересчитывает его дифференцируемо по сохранённому сэмплу (PPO не пересэмплирует). Запрещённые маской варианты имеют вероятность 0, единственный допустимый вариант — `log_prob = 0` и энтропию 0 (тест с принудительными масками). Нормировка проверена полным перебором (все упорядоченные выборы целей и k на малой маске суммируются в 1), а `log_prob` совпадает с независимым подсчётом в самом сэмплере.

Каждая колония рисует из своего потока PCG32 (`policy:learned:<колония>` от `policy_seed`), поэтому одинаковые наблюдения у двух колоний дают разные сэмплы, а тот же seed воспроизводит тот же мир.

## PPO (`eco/rl/ppo.py`, `eco/rl/rollout.py`)

* Сбор: одна сеть, колонии, решающие в один тик, обслуживаются одним батчевым проходом (`PolicyController(..., batcher=...)`), но с индивидуальными GRU и RNG. Интервалы закрываются следом тика (`ViabilityTracker`), advantage и return считает time-aware GAE (`viability.gae_intervals`).
* Обновление: PPO-clip по целым траекториям колоний (минибатч — набор траекторий), `ε = 0.2`, энтропия отдельно для категорий и для долей, `target_kl = 0.03`. Перед шагами на неизменённых весах считается `identity_ratio_max_dev`: ratio обязан быть 1 с точностью шума float (в обучении ~1e-6), иначе в `log_prob` или в разворачивании GRU ошибка, и её нельзя принять за обучение (тест подставляет испорченный `old_logp` и видит отклонение > 0.4).
* Проверка оптимизатора на задаче с известным ответом (`test_ppo_finds_the_best_choice_of_a_known_task…`): награда за один выбор egg на реальном наблюдении; вероятность лучшего варианта растёт с 0.25 до > 0.6, с противоположным знаком награды — падает до < 0.1.
* Карты не повторяются: карта мира `j` итерации `i` — `train_seed0 + i·worlds + j`; отложенные карты оценки (`eval_seed0 = 90000…`) не пересекаются с обучающими (`200000…`).

## Policy-интерфейс и replay

Обученная сеть подключена как политика вида `learned` с вариантом `<sample|greedy>-<первые 16 hex SHA-256 весов>` (`eco/rl/learned.py`). Это обычный `PolicyE1`: на вход `ObservationE1` и маски, на выход латенты декодера; один объект на колонию, собственная память и поток. Replay-файл — тот же `formicmind.eco.replay/1`, что показывает существующий viewer; в заголовок записаны политики, в результат — число и хэш решений. `replay-verify --model <каталог>` заново исполняет мир с этой моделью и требует побайтно тот же файл. Без модели проверка невозможна и сообщает об этом.

**Ограничение воспроизводимости.** Мир детерминирован целочисленно; решения сети считаются в `float32` в PyTorch. На одной машине и одной сборке прогон воспроизводится байт в байт; на другом процессоре последний бит матричных умножений может отличаться, и тогда выборка, попавшая в границу вероятности (порядка 1e-7), дала бы другой выбор. Для файла с решениями это означает: мир проверяется при тех же решениях всегда, а сами решения — при той же сборке.

## Pilot: бюджет, результаты, честный вывод

**Бюджет и seed (зафиксированы до запуска, ничего не подбиралось).** `python -m formicmind.eco train --iterations 120 --worlds 16 --ticks 6000 --workers 8 --seed 1 --eval-every 20 --eval-worlds 8`: 120 итераций × 16 миров × 8 колоний = 1920 полных миров по 6000 тиков, 15 360 траекторий колоний, 2.38 млн решений. Только CPU (Windows, 12 потоков), 53 минуты: сбор 15 мин, обновления 36 мин. Сеть 430 693 параметров; PPO: `clip 0.2`, `lr 3e-4`, 4 эпохи, минибатч 16 траекторий, `ent 0.01`, `reward_scale 10`, `target_kl 0.03`; остальное — значения по умолчанию кода. Обучающие карты `200000…`, отложенные `90000…90007`. Исходы обучения — `docs/ecosystem_examples/for49_pilot/` (`config.json`, `metrics.jsonl`, `train.log`, `eval_*.json`, `eval_report.json`, модель `model/`).

Первый запуск того же бюджета упал по памяти на 47-й итерации (процессор делил память с чужим процессом; крупный минибатч не помещался в обратный проход). Исправлено накоплением градиента по кускам по 4 траектории (математика минибатча та же, тест `test_accumulating_gradients_over_chunks_equals_one_big_minibatch`) и повтором заданий при падении воркера; запуск повторён с нуля с теми же настройками. Результаты ниже — из второго, завершённого запуска; первый давал ту же кривую (награда > 0 около 35–45 итерации).

**Что показывает обучение** (`metrics.jsonl`, стохастическая политика на обучающих картах): награда на колонию −0.998 (итерация 1) → −0.947 (20) → −0.794 (30) → +0.18 (35) → +0.39 (40) → +0.42 (60) и до конца (+0.423); доля выживших колоний 0 → 0.79 на 35-й итерации → 1.0; энтропия 14.7 → 5.2 нат; `identity_ratio_max_dev` во всех 120 итерациях < 4e-6 (log-prob при первом проходе совпадает с собранным); объясняемая дисперсия критика → 0.99.

«Выжили пустыми» — колония жива (матка цела), но взрослых нет.

**Вывод, без приукрашивания.** Сеть реально научилась: из состояния, где все колонии гибнут за ~100 тиков (награда −0.998), она дошла до награды +0.42 на новых картах, превзойдя необученную сеть и `random_valid` на 1.4 пункта и повторив результат на всех 8 отложенных картах (0.4217–0.4237). **Но научилась она не играть, а эксплуатировать награду**, и по числам оценки хуже простой эвристики `peaceful` (0.510). Траектория колонии 0 на карте 90000 (`workers / food / v` по тикам):

```
t=0     10 рабочих  + 2 солдата   75 еды  v=0.24     яйца не кладёт никогда (egg_level = 0)
t=300    7 рабочих               269 еды  v=0.49     все силы в доставку еды
t=900    7 рабочих               597 еды  v=0.47     склад полон (потолок 600)
t=1800   2 рабочих               583 еды  v=0.45     рабочие стареют и умирают
t=2100   0 рабочих               592 еды  v=0.42     матка одна, содержание 0
t=3300+  0 рабочих               592 еды  v=0.40     до тика 6000, штрафа нет (матка жива)
```

Причина — в самой награде (контракты §9.1) вместе с правилами выживания, а не в ошибке реализации (трекер совпадает с независимым пересчётом): при нулевом числе взрослых содержание = 0, поэтому `burn ≤ income` и `runway = ∞`; `security = 1` вносит `0.4`, матка не умирает и не «коллапсирует» (коллапс требует `food < worker_egg_cost`, а склад полон), штрафа нет. Потолок такой стратегии 0.4 за тик, и она находится быстро и надёжно: нужно только перестать класть яйца, накопить склад и дождаться, пока рабочие умрут. Настоящая колония даёт больше только при росте популяции (`pop` до 0.6), а это требует яиц, то есть содержания и риска для `security`; PPO за 53 минуты такой путь не нашёл. Таблица §9.4 «Накопление еды» считала, что склад даёт только `security`; она не учитывала, что `burn → 0` вместе с вымиранием рабочих. Эвристика `peaceful` берёт 0.56–0.59 на пяти картах из восьми (растёт до ~20 рабочих), на трёх остальных — около 0.41 (почему, не исследовалось).

Чего в этом результате **нет**: разведки, контактов, войн (атаки 0, обученная политика почти не выходит за пределы известных узлов), конкуренции за площадки. Реплей `viewer/public/samples/eco_learned_ppo_seed90000.jsonl` (кнопка «Пример: обученная сеть (PPO)») честно показывает это: на последнем кадре 8 колоний «живы», у всех 0 рабочих и 0 солдат, на складах 590–600 еды.

**Что я не делал и почему.** Награду, экономику и гиперпараметры не менял и не подбирал заново: задача — первый рабочий цикл и честная оценка, а контракт §9.1 утверждён, его пересмотр — решение владельца. Автоматических циклов донастройки не запускал.

**Что предлагается дальше (требует решения; не сделано).**

1. Исправить сам стимул: например, `security` умножать на `min(1, E_pop/10)` или считать колонию без взрослых и без расплода вымершей (`collapse`) независимо от склада; добавить регрессионный тест, что состояние «пустая колония на полном складе» не оплачивается. Это изменение контракта (§9.1, §9.5) и всех ссылок на viability.
2. После этого повторить тот же pilot с тем же бюджетом и тем же seed и сравнить с `peaceful` на тех же 8 картах; без вывода «колония научилась воевать», пока в метриках нет атак.
3. Только затем — лига и самоигра (E3-b).
