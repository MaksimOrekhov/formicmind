# L0 экономика и расплод (FOR-12)

Поверх движущегося мира (FOR-11) реализованы фазы `Completion → Harvest → Upkeep/Starvation → Lay → Regeneration`
по FOR-1 v0.2.1 (+ errata A–G, R1). Режим исполнения тика — **`PARTIAL (NO COMBAT/TERMINAL)`**: боя, `QueenTerminal`
и terminal-проверки (гибель матки, экономический коллапс, таймаут) **нет**, матч не заканчивается, `physics_complete`
всегда `False`. Баланс остаётся кандидатским (`candidate-FOR1-v0.2.1-unvalidated`) и **не калибровался**; `Gate 0`/`Gate 1`
не пройдены. Версии (`rules_version`, `balance_version`, observation/action) и золотые хэши `reset` не менялись.

## Режимы тика

Одна реализация тика, две явные таблицы фаз (`tick.PHASE_TABLES`). Без выбора режима `step_tick` бросает `IncompleteRulesError`.

| Режим | Вызов | Исполняется |
|---|---|---|
| `MOVEMENT ONLY` | `step_tick(..., movement_only=True)` | Policy, Arrival, AutomaticDepart, учёт `window_ticks` (как в FOR-11, для сравнения) |
| `PARTIAL (NO COMBAT/TERMINAL)` | `step_tick(..., partial_economy=True)` | всё выше + Completion, Harvest, Upkeep, Lay, Regeneration |

`TickResult.mode`, `TickResult.missing_phases` (`Combat`, `QueenTerminal`) и `PhaseRecord.implemented` показывают, что именно
не исполнено. `step_tick(..., check_invariants=True)` после тика сверяет ledger и правила юнитов (`ledger.check_transition`).

## Правила (целые числа, без float и RNG)

**Completion.** Весь расплод с `hatch_tick == t` становится взрослыми с полным HP **в домашнем узле**, `unit_id` сохраняется
(выдан при кладке). Просроченный `hatch_tick < t` — ошибка состояния (до изменений). Новорождённые платят upkeep того же тика.
Цель (errata E): солдат — `army_choice`; рабочий — категория с максимальным положительным дефицитом между квотами
наибольших остатков для `N+1` рабочих и текущими `target_node` рабочих; равный дефицит — порядок **side-local**
`home, N1, N2, C, N4, N5`; некорректные веса → остаётся дома. `AutomaticDepart` того же тика отправляет их без нового policy tick.

**Harvest.** Только рабочие, *стоящие* в узле в момент фазы. Заявка стороны `min(рабочих, max_harvest узла)` (индивидуально
1/тик). Если в узле стоит живой вражеский солдат — сторона заблокирована и не заявляет ничего (errata B; свои солдаты не
помогают; вражеские рабочие не блокируют; солдат на ребре не блокирует). При `stock ≥ Σзаявок` — полностью; иначе
`floor(stock·cᵢ/Σ)`, единственный оставшийся (при двух сторонах ≤1) идёт стороне со **строго** большей дробной частью, при
равенстве **остаётся в узле** (errata C). Сравнения целочисленные (`stock·c mod Σ`), результат симметричен при обмене сторон.
Дома A/B (`max_harvest=0`) еды не дают. `max_harvest`, `capacity`, `regen` берутся из `SimConfig`.

**Upkeep.** `rem += 4·W + 8·S` (из конфига: `worker/soldier_upkeep_tenths`), `due = rem // 10`, `rem %= 10`. Платят все
взрослые (в т. ч. в пути и только что вылупившиеся); расплод и матка — нет. `paid = min(due, food)`.

**Starvation (errata D).** `debt += due − paid`. Пока `debt ≥ starvation_unit_cost` и есть взрослые: удалить одного, `debt −= cost`.
Порядок жертв: солдаты → рабочие; внутри касты дом → другие узлы → в пути; затем `unit_id`. Полностью оплаченный ненулевой
upkeep (`due > 0`, `missing == 0`) обнуляет остаток долга. Тик с `due == 0` долг не меняет. Расплод голодом не убивается.

**Lay (errata F).** При живой матке, `lay_order ≠ none`, `t ≥ next_lay_tick`: **вся** партия `eggs_per_lay × cost`
списывается атомарно и один раз, иначе ни одного яйца, ни списания, `next_lay_tick` не тратится (событие `lay` с `laid=false`).
Каждому яйцу — стабильный `unit_id` (глобальный аллокатор, сторона A затем B), `BroodRecord(laid_tick, hatch_tick)`,
`next_lay_tick = t + lay_interval_ticks`. Нет `population_cap`, `brood_capacity`, потолка склада; расплод стоит один раз.

**Regeneration.** `stock = min(capacity, stock_after_harvest + regen)` для каждого узла с `capacity > 0`, после добычи, upkeep и Lay.

## События и checkpoint

Новые типизированные события (`events.py`, омнисциентный лог; политика их не видит): `hatch`, `harvest` (сторона × узел,
заявка/блокировка/добыто/запас до и после), `upkeep` (каждый тик, обе стороны), `starvation` (одна смерть, порядок `seq`),
`lay` (партия или отказ), `regenerate`. Порядок в списке = исполнение = сортировка по `event_sort_key`
(`(phase, kind_rank, *event.sort_tail())`); смерти идут в порядке жертв, а не по `unit_id`.
Этого достаточно, чтобы восстановить экономику без повторной реализации (в т. ч. во Vue).

Состояние для checkpoint уже было в схеме (`food`, `upkeep_remainder10`, `starvation_debt`, `next_lay_tick`, `brood`,
`next_unit_id`, `RunState.windows`) — **версии схем/хэшей не менялись**. `WindowStats` (`harvest`, `upkeep_paid`, `egg_spend`,
`starvation_debt_delta` — знаковое изменение долга за тик, `window_ticks`) обновляются обеими сторонами; потери/смерти
в окно не пишутся (в FOR-2 нет слота), только в события. `run → checkpoint → restore → тот же state_hash/event_hash/ObservationV2`
проверено на t=30/45/60.

## Ledger и инварианты

`sum(node_food) + sum(warehouse) == start + regen_added − upkeep_paid − egg_spend`: Harvest лишь переносит еду,
Upkeep и Lay уничтожают, Regeneration создаёт. `ledger.check_transition(before, after, events)` дополнительно проверяет
каждую сторону и узел, ровно созревший расплод в Completion, добавление/удаление взрослых только вылуплением/голодом,
неизменность HP, уникальность `unit_id`, полное HP новорождённого и его место (дома либо вышел из дома в этом тике).
Валидатор состояния теперь отвергает расплод с `hatch_tick < tick`.

## Smoke

```bash
python -m formicmind.economy_smoke
```

120 тиков, два скриптовых полиси (A «boom», B «barracks», солдаты в гарнизоне), каждые 10 тиков: взрослые W/S, расплод W/S,
склад, добыча, upkeep, яйца, вылупления, смерти, еда узлов; в конце ledger и хэши. Это диагностика механики, не баланс.

## Открытые вопросы к спецификации (реализовано консервативно, без изменения правил)

1. **Порядок жертв внутри касты.** Errata D говорит «unit_id/location», тело v0.2 — «сначала дома, затем узлы, потом в пути, по
   фиксированному ID». Реализовано буквальное объединение (дом → узлы → путь → `unit_id`). Альтернатива — чистый `unit_id`.
2. **Что считать «полностью оплаченным upkeep».** Реализовано: `due > 0 && missing == 0`. Если считать и `due == 0`, колония с
   долгом и малым upkeep (0,4 ед./тик) обнуляла бы долг через тик и никогда бы не теряла юниты.
3. **Tie-break «лексикографический node ID» для новорождённых.** Реализован side-local порядок (конвенция R1), иначе правило
   несимметрично (для B «C» < «N4»). Требует подтверждения как расширение R1 на errata E.
4. **Порядок `unit_id` между сторонами при одновременной кладке** (A, затем B) нельзя сделать зеркальным; ID значимы только внутри
   стороны, тесты симметрии сравнивают состояния без ID.
5. **Без боя блокировка вечная:** два солдата противников в одном узле навсегда блокируют добычу и выход друг друга до
   реализации Combat.
6. **Кладка при `queen_hp == 0`** запрещена; вылупление не проверяет матку (по спецификации эпизод уже завершён).

Не входит: Combat/урон матке/terminal, коллапс и таймаут, runner/турниры, ML, JSONL, UI.
